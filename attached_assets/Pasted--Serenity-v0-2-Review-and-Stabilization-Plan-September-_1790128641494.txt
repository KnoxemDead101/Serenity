## 1. Critical finding: the published site isn't running Serenity

Replit Agent set the project up as a Node/TypeScript "pnpm workspace", which runs differently in preview and in production:

| Mode | What actually runs |
|---|---|
| **Preview (workspace)** | `artifacts/serenity/package.json` → `dev` → `python main.py`. **Real Serenity works here.** |
| **Published** (`serenity--lknox3.replit.app`) | `artifacts/serenity/.replit-artifact/artifact.toml` → production → `vite build`, served as **static files**. That builds a React placeholder whose home page says "Replit Agent is building…". Every URL (including `/serenity-api/...`) is rewritten to that placeholder. **FastAPI isn't running at all.** |

Checked on 9/22: fetching the live URL and `/serenity-api/accounts/options` both returned the placeholder page, not Serenity or JSON.

So the preview was tested successfully, but the published app has never actually been Serenity. It also means no data has been lost, because the published site never had a database.

## 3. Review of the Replit-written Bills / Debt / Investments

**Good:**
- Follows the layers (route → schema → service → model).
- Stores money in cents.
- Rejects negative amounts and more than 2 decimal places.
- The frontend only displays values.

**Bugs, checked against the actual code:**

| # | Issue | Evidence | Impact |
|---|---|---|---|
| B1 | **Monthly bill normalization truncates** | `finance_service.get_finance_summary`: quarterly `amount_cents // 3`, annual `// 12` | A $100.00 quarterly bill counts as $33.33/month. Three of them total $99.99 instead of $100.00. The error grows with each bill because rounding happens per bill. |
| B2 | **Interest-rate conversion** | `int(data.interest_rate * 100)` into `interest_rate_bps` | The math is exact today only because the schema rejects more than 2 decimals. But that rule **rejects real rates like 6.875% APR**. The conversion is fragile, and the precision is too low. |
| B3 | **Investment quantity stored as text** | `models/investment.py`: `quantity: String(50)` | The database can't sort, sum or check it. (A plain `Numeric` column would silently become a float in SQLite, which is probably why the Agent used text.) |
| B4 | One-time bills | counted in `bill_count` but not in the monthly total | Needs a documented rule, not necessarily a code change. |
| B5 | Only one finance test | `tests/test_finance_api.py` | Nothing tests B1, B2 or B3. |

## 4. Conflicts with the v0.2 domain model

| Area | Current | v0.2 | Recommendation |
|---|---|---|---|
| Investments | `Investment` stores `cost_basis` + `current_value` directly | Holding (quantity × current_price) + InvestmentTransaction; cost basis is derived | **Mark it temporary.** Fix only B3 now; replace it in the Portfolio milestone. Don't enter real portfolio data yet. |
| Credit cards | negative opening balance on an Account | Debt is the liability | Pick one rule to avoid **double counting** when net worth arrives. Recommended: a credit card is an Account (for transactions) *and* its balance owed lives in Debt, and net worth counts it once. Decide before Transactions. |
| Account fields | `notes`; no `active`, `description`, `business_id`; no "Retirement" type; "Business Checking" type | `active`, `description`, optional `business_id`, `retirement` type | Add `active` and "Retirement" now (small and cheap before the migration baseline). Business entity comes later. |
| Choice values | Display text ("Checking") | lowercase codes (`checking`) | Keep display text for now; switching is a separate, deliberate change. |
| Bills | no `account_id`, `autopay`, `active` | v0.1 spec had them; v0.2 wants Bill ↔ Transaction matching | Defer to the Income + Budget milestone. |
| Coupling | `account_service` imports `finance_service`; `AccountTotals` holds bill/debt/investment fields | Separate systems, not tightly coupled | Add `services/dashboard_service.py` + `schemas/dashboard.py` that **combine** the two, and restore `AccountTotals` to accounts only. The API response shape stays the same. |
| Income | `models/income.py` is the old plain class | Income is part of the model | Leave it until the Income milestone. |
| API prefix | `/serenity-api` | n/a | Keep it; changing it again is churn without benefit. |

## 6. How PostgreSQL + Alembic will work

- **One setting chooses the database.** `DATABASE_URL` is set → use it (Replit Postgres). Not set → `sqlite:///./serenity.db`. The code doesn't change between environments.
- **Replit has two Postgres databases.** The workspace preview uses the **development** database and the published app uses the **production** database, each with its own `DATABASE_URL`. Test data in the preview never mixes with real data.
- **Alembic = version control for the database structure.** Each change (e.g. "add transactions table") becomes a numbered migration file in Git. `alembic upgrade head` brings any database, whether a new SQLite file or the production Postgres, up to the latest structure **without deleting data**. `create_all()` can create missing tables but can never change an existing one, which is why it isn't enough once real data exists.
- **The workflow for every future model change:** edit the model → `alembic revision --autogenerate -m "..."` → read the generated file → `alembic upgrade head` locally → commit both → the deploy runs the upgrade.

## 7. How SQLite stays available
- **Tests:** `conftest.py` always uses an in-memory SQLite database (it already ignores a Postgres `DATABASE_URL`). Tests stay fast and never touch real data. `test_migrations.py` also checks the migrations on SQLite.
- **Local development on your PC:** don't set `DATABASE_URL`, and it uses `serenity.db`. Run `alembic upgrade head` once, then `python main.py`.
- **Why both work:** SQLAlchemy hides the differences. Where the two databases differ (decimals, altering tables), we store integers (cents, milli-percent, quantity units) and use Alembic's batch mode, so the same code and migrations behave the same way on both.
